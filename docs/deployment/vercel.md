# Raven frontends on Vercel

Three Next.js 16 apps, one Vercel project each, all deployed from this
pnpm workspace.

| Vercel project | Root directory | Production URL |
|---|---|---|
| `raven-landing` | `apps/www` | https://raven-landing-atulsinghh.vercel.app |
| `raven-dashboard` | `apps/dashboard` | https://raven-dashboard-atulsinghh.vercel.app |
| `raven-docs` | `apps/docs` | https://raven-docs-atulsinghh.vercel.app |

Note the landing app lives at **`apps/www`**, not `apps/landing`.

## Build configuration

Nothing is overridden. Vercel's Next.js preset is left to do its job, and
that is deliberate — the apps build with plain `next build` and have no
custom output requirements.

| Setting | Value | Source |
|---|---|---|
| Framework | Next.js (16.3.3) | auto-detected |
| Install command | *(default)* | Vercel runs `pnpm install` at the **workspace root** |
| Build command | *(default)* | `next build` in the root directory |
| Node.js | 24.x | Vercel default; repo requires `>=20` |
| pnpm | 11.22.0 | read from `package.json#packageManager` |

Vercel resolves the workspace correctly on its own — build logs show
`Detected pnpm-lock.yaml version 9 generated by pnpm@11.x` and
`Scope: all 15 workspace projects`, installing from `../..`. That is what
makes the root lockfile authoritative, so there is no second, divergent
install inside the app directory.

`.vercelignore` excludes only build artefacts and caches. It must **not**
exclude sibling workspace packages: `pnpm-workspace.yaml` globs `apps/*`
and `packages/*`, so removing another package's `package.json` breaks
`pnpm install` at the root, which is where the install happens.

## Environment variables

Every variable, classified. No secret is present in any frontend project.

### `raven-landing`

| Variable | Class | Value |
|---|---|---|
| `NEXT_PUBLIC_DASHBOARD_URL` | PUBLIC | dashboard URL |
| `NEXT_PUBLIC_DOCS_URL` | PUBLIC | docs URL |

No API variable, because the landing app makes **no** backend calls. The
`@corvidhq/*` and `createRTCClient` references in `src/components/` are
inside template-literal code samples, not imports — no frontend has a
`@corvidhq` dependency in its `package.json`.

### `raven-dashboard`

| Variable | Class | Value |
|---|---|---|
| `RAVEN_API_URL` | **SERVER-ONLY** | the Azure Container Apps HTTPS endpoint |
| `NEXT_PUBLIC_DOCS_URL` | PUBLIC | docs URL |

`RAVEN_API_URL` carries no `NEXT_PUBLIC_` prefix, and must never get one.

### `raven-docs`

| Variable | Class | Value |
|---|---|---|
| `NEXT_PUBLIC_WWW_URL` | PUBLIC | landing URL |
| `NEXT_PUBLIC_DASHBOARD_URL` | PUBLIC | dashboard URL |
| `NEXT_PUBLIC_DOCS_URL` | PUBLIC | docs URL |

The docs app makes no backend calls either.

### Never in a frontend project

`DATABASE_URL`, `DIRECT_URL`, `REDIS_URL`, `TURN_SECRET`, `JWT_SECRET`,
`RTC_TOKEN_SECRET`, `CHAT_TOKEN_SECRET`, `API_KEY_HASH_SECRET`,
`SFU_REGISTRATION_SECRET`. All of these live in Azure Key Vault and are
injected as Container Apps secrets. Audited: none present.

`RAVEN_API_KEY` also must not be set. It appears in
`apps/dashboard/.../sdks/page.tsx` only inside code samples shown to
developers; nothing reads it at runtime.

**`NEXT_PUBLIC_*` values are inlined into the browser bundle at build
time.** Two consequences: they can never hold a secret, and changing one
requires a **redeploy**, not just an env update.

## Why there is no `NEXT_PUBLIC_API_URL`

The dashboard is a backend-for-frontend. Every browser `fetch` is
same-origin to a Next.js route handler under `/api/*`; those handlers run
on Vercel's server and call the Azure API through
`apps/dashboard/src/lib/api-client.ts`, which is the only file that knows
the API's address:

```ts
const API_BASE_URL = process.env.RAVEN_API_URL ?? 'http://localhost:4100';
```

```
Browser ──same-origin──> /api/* (Vercel server) ──RAVEN_API_URL──> Azure API
```

14 of the 15 route handlers go through `api-client`. The exception,
`api/cli-auth/token/route.ts`, makes no outbound call at all — it returns
the caller's own session token from the httpOnly cookie.

The session JWT lives only in an `httpOnly`, `secure`, `sameSite=lax`
cookie (`src/lib/session.ts`). No client component ever sees it, and the
register/login responses deliberately omit `accessToken` from their bodies.

Adding `NEXT_PUBLIC_API_URL` would publish the API address to every visitor
and imply a direct browser→API path the auth model does not support.

## CORS

**None of the three frontends require a CORS entry on the Azure API.**
Verified from the code, not assumed: the landing and docs apps make no
backend calls, and all dashboard browser traffic is same-origin.

CORS on the API still matters for **third-party** browser apps built on the
SDKs. It is enforced in two places:

- HTTP, via `app.enableCors()` in `apps/api/src/main.ts`.
- The **chat WebSocket**, which validates the `Origin` header against
  `cors.origin` and rejects with `ORIGIN_NOT_ALLOWED`
  (`chat/gateway/chat.gateway.ts`). The signaling gateway does not check
  origin.

`CORS_ORIGIN` must never be `*` in production — the API refuses to boot.

## Deployment Protection is off

New projects inherited `ssoProtection: all_except_custom_domains`, which
made every `*.vercel.app` URL 302 to `vercel.com/sso-api`. That is correct
for private previews and wrong for a public landing page, public docs, and
a dashboard with its own login — it would have blocked all real users.

Disabled on all three. Re-enable per project with:

```bash
curl -X PATCH -H "Authorization: Bearer $VERCEL_TOKEN" \
  -H 'Content-Type: application/json' \
  https://api.vercel.com/v9/projects/raven-docs \
  -d '{"ssoProtection":{"deploymentType":"all_except_custom_domains"}}'
```

## Custom domains

`ravenstack.online` is registered on all three projects:

| Project | Custom domain |
|---|---|
| `raven-landing` | `ravenstack.online` (+ `www`) |
| `raven-dashboard` | `app.ravenstack.online` |
| `raven-docs` | `docs.ravenstack.online` |

They report `misconfigured: true` until the registrar's nameservers point at
the Azure DNS zone that holds the records — see
`infrastructure/azure/README.md` "Custom domains". Vercel issues the TLS
certificates automatically once DNS resolves.

The Vercel-generated domains (`raven-*-atulsinghh.vercel.app`) keep working
and are what the deployment is verified against today.

The full target layout, including the non-Vercel hosts:

```
ravenstack.online       -> raven-landing        (Vercel)
app.ravenstack.online   -> raven-dashboard      (Vercel)
docs.ravenstack.online  -> raven-docs           (Vercel)
api.ravenstack.online   -> raven-api            (Azure Container Apps)
turn.ravenstack.online  -> 40.83.92.152         (coturn VM)
```

Once DNS is live, `infrastructure/azure/14-custom-domains.sh` performs the
cutover in one step. It also rewrites the `NEXT_PUBLIC_*` inputs' consumer —
`RAVEN_API_URL` — and redeploys the dashboard, because those values are
inlined at build time and an env change alone would not take effect.

## Deploying

Git integration is **not** connected (see below), so deploys are CLI
uploads from a working tree:

```bash
vercel link --project raven-dashboard --yes
vercel deploy --prod --yes
```

Each `vercel link` rewrites `.vercel/project.json` at the repo root, so run
the two commands as a pair per project. `.vercel` is gitignored.

## Git integration — not connected

Item: `git push` does not deploy. Creating a project with a
`gitRepository` link fails:

```
Failed to link atulsinghhhh/Raven. You need to add a Login Connection
to your GitHub account first.
```

`GET /v1/integrations/git-namespaces` returns `[]`, confirming no GitHub
Login Connection on the Vercel account, even though older projects
(`mehfil`, `qwaali`) still carry github links from when one existed.

This cannot be fixed from the CLI or API — it needs a browser:

1. Vercel dashboard → Settings → Login Connections → connect GitHub, **or**
   import any project via the GitHub flow once.
2. Then, per project: Settings → Git → connect `atulsinghhhh/Raven`.
3. Set the production branch (`main`) and, for a monorepo, confirm each
   project's Root Directory is still `apps/www` / `apps/dashboard` /
   `apps/docs`.

Until then, production deploys are manual, and preview deployments do not
exist — which is why `RAVEN_API_URL` is set for the Production target only.
